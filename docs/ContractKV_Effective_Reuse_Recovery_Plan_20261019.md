# ContractKV：有效复用恢复的有界执行计划

用户在上一轮授权修复结束后明确要求继续完整服务回归、低覆盖归因及最小执行优化。本轮是新的授权，不重启历史worker/自动化，不覆盖V5或授权修复原包，不修改正文/Response Letter。

## 目标与执行门槛

1. CPU逐决策核对V5全部主服务资格，以及原Table III完整Controller/Raw参考/认证HTTP费用。区分语义/证据拒绝、继承L0、计划准备和实际GPU等待。
2. 新全服务入口强制统一授权缓存身份，并接入实际签名绑定检查；Raw、L0、fallback、Verifier、compiled均经同一可信入口。保持旧runner、scope、margin/EOS、输入、评分和PSTP作为对照。小型实际GPU冒烟先于正式服务。
3. 候选执行优化优先检查“先构造完整候选/调用tokenize，再发现见证不符合scope或输出契约”的无效工作。若成立，可在Raw见证后先做同一确定性拒绝检查，通过后才准备候选。保留全部原行为约束与经济决策，测量准备/认证的实际关键路径，不能只靠少认证取得正结果。
4. 独立新开发来源仅用于既有L1/L2/L3候选可行性。M/L原Repo L0不直接放开；必须同时通过原scope、输出契约、Raw/candidate/EOS margin与自由生成检查。开发中不使用gold位置选源或在线改判。
5. 只有开发确认具体机制改善且没有行为/发布回归，才冻结来源不重叠的新服务对照。各臂都采用统一授权边界：Raw、V5行为/成本原规则+授权、最小执行修复（若开发有足够候选证据，再单列新冻结catalog）。同来源、同GPU配置、同到达/调度/SLO、全部准备与失败费用入clock。旧无盐V5仅作历史或小型接线对照，不追认其已运行新入口。

## 边界与停止条件

- exact-observation的当前metadata含tenant/session和turn，当前负载通常无精确重复；不能直接把这类拒绝改为共享query放行。
- 不降低0.0625/0.125 margin，不忽略EOS，不扩大行为scope，不改变PSTP、不增异步调度器或预测网络，不复活已失败的成本适配方案。
- CPU后验重算不是GPU提速证据；开发候选成功不是独立泛化。开发与正式来源、规则冻结时间分别保存。
- 开发最多三个模型各一个fresh-server候选诊断；原有全服务授权接线冒烟和候选可行性分别计量。正式服务规模待开发门槛决定，先冻结再执行，不凭正式结果换源或调门槛。
- 如果没有合法覆盖机会或成本改善不足，明确NO-GO，保留已完成授权回归和诊断，不无条件扩新服务矩阵。

## 初始证据与待验证假设

源码确认V5在`build_gate`中、业务见证生成之前即调用`candidate_plan`两次tokenize；后续`StagedRegistrar`才检查reference scope与输出契约。旧Qwen固定到达每负载54项决定中24 scope、9 output-contract拒绝，可能存在确定无效的候选准备。一次实际PASS计划准备约690ms说明这不是只做了几个布尔判断。但节省多少必须从全部日志核算及新服务测量，不将一个案例外推。

源码也确认V5业务流仅compiled有旧salt，证书复用只核scope索引/前缀hash，尚未使用上一轮的新身份入口。因此“全V5回归接入”确有独立工作，不能以828次微工作流替代。远程两3090在本轮开始时只读确认空闲，启动前仍须重查实际UUID/PID与冻结源/模型runtime状态。
