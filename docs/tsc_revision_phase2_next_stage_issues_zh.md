# 第二阶段后续问题台账

本台账保留第二阶段没有完全解决的问题，并列出已经做过的修正与下一步可检验的方案。R2/R3 是第二阶段内部的两版独立验证；后续工作另设阶段，不把旧验证集调参重跑称为新验证。最终结论以第二阶段总报告和各版完整审计为准。

## 1. 动态输入下的质量保持范围

第一批独立验证在 5401 次编译未来请求中保留 7 次 >0.03 分数下降。Qwen 的 4 次来自一个 RepoBench 来源：认证参考本身含无法解析的语句连接，未来 raw 切换成较短且分数更高的代码，compiled 保持参考；其 candidate 最小 margin 超过 9，并非近并列就能解释。Llama 的 3 次来自一个 NarrativeQA 来源，同义否定的词面 F1 从 0.2 变成 0，candidate 最小 margin 为 0.09375。重复和租户相关，不能把这 7 次解释成 7 个独立失败来源。

已经实施的改法是 raw/candidate 逐 token 最小 margin、自然 EOS 检查、完整实际 prompt IDs/hash、单次认证、RepoBench 单条完整 Python 语句准入，以及 candidate/EOS 门槛从 0.0625 收紧到既定开发网格中的 0.125。最后两项只使用已观察的第一批失败确定，随后换用另外 50 个不重叠来源，冻结后再运行。原始失败和拒绝造成的覆盖损失均保留。

第二批独立冷会话又发现 Qwen 的一个 NarrativeQA 来源 doc99，在三个重复的 t7 发生 F1 0.1212→0.0714。三个 compiled 输出均逐 token 保持 t1 获准参考，参考与对应 raw 的实际 prompt/output IDs 也相同；未来 raw 换成较长的否定表述，从 token 位置 24 开始不同。raw 参考最小 margin 为 0.09375/0.125/0.125，candidate 为 0.40625，配对策略在同一 GPU 上运行。这是有完整记录的新失败，现有候选门槛不能阻止。语义同为信息不足只用于解释，冻结 F1 下降照常计入。没有为了消除这组测试失败而修改准入或评分。

需要保留的边界是：有限 witness 的行为认证不能直接推导任意未来 observation 的任务分数保证。语法准入也会拒绝合法的多语句或不完整代码 continuation，只适用于当前单语句准入条件。它没有执行代码、改写答案或读取 gold 分数。

下一阶段优先检验“哪些动态变化仍能共用一个资格”这一范围，而不是继续只抬高 margin。可把 query/observation 的变化分成可审计条件，在开发集建立失效边界，再冻结新来源验证。对实际失败保存同输入多次 raw、compiled 冷/热缓存、固定 GPU 与并发形状对照；离线生成两条路径用于因果诊断，其成本不能隐去后当成部署收益。若增加输出类型契约，应逐任务声明合法输出范围并单报覆盖损失。

仅把 raw 门槛继续抬到超过 0.125，可以事后拒绝这组三个已见参考，但还不能说明能处理其他未来响应变化。第二阶段没有把这种针对测试结果的新阈值直接替换成正式策略，也没有靠事后禁用失败来源宣称目标达成。

## 2. 冷会话收益小、p99 仍高于 raw

第一批三模型完整 wall 吞吐分别为 raw 的 1.059、1.009、1.038 倍，三个重复均高于 1；Mistral 的增益很小。冷会话 p99 相对原连续降档控制下降，但仍高于 raw。已经取消在线多级失败重试、恢复事前收益门禁，并对同一 scope/wave 的参考 logprob 采集去重。门禁跳过 GPU 验证不意味着整个控制器是零成本。

第二批冷会话倍率为 1.074/1.006/1.001，Llama 三重复范围为 0.9968–1.0063，稳定正收益目标仍未达到。第二批 1188 个进入计划的 scope 全部通过事前收益预测，实际提前跳过 GPU 的 169 个来自 raw margin（142）或语法准入（27），不来自收益预测拒绝。1019 次真实认证中仍有 305 次拒绝，且只允许单次尝试。门禁已实现，但本轮没有显示它能筛掉这些无效认证；应进一步检验认证失败概率、实际复用量与在线认证预算，而不能把“恢复门禁”本身当作收益原因。

下一阶段先按任务族拆出规划、参考 logprob、失败认证、raw 回退和可复用轮次的实际贡献，判断小收益是覆盖限制还是成本预测偏差。可以在开发数据上校准更保守的成本上界与剩余复用估计，但必须重新冻结选择规则，并用新来源评估净收益和覆盖。不能依据测试集实际未来收益倒推在线门禁。

吞吐收益门禁还需要与尾延迟预算分别评估：Qwen 第二批冷会话吞吐提高约 7.4%，p99 却从 2505 ms 升到 4592 ms。可检验带失败概率与单次在线时间上限的准入，但这仍是待验证方案，不能预先承诺同时改善所有指标。

## 3. 十租户尾延迟没有普遍显著改善

第一批十租户有端到端吞吐和平均 readiness 改善，但相对降档控制的三模型 p99 下降区间都跨 0。开发尾部分析显示，Mistral/Llama 的最慢请求多为继承 L0 的 RepoBench，额外认证前等待很少；Qwen 部分尾部仍有验证及 wave 同步等待。不能把所有尾部都归因于多级认证。

下一阶段应区分原始路径本身的延迟下限与资格工作造成的排队。可另设异步资格准备或独立请求到达协议，让两条路径使用相同调度、到达时刻和成本口径，检验是否真正降低实际请求尾延迟。原来的两请求 readiness wave 屏障数据继续保留，不能通过重定义计时起点使旧 p99 变好。均值改善也不能替代尾部分位数的证据。

## 4. Llama 更长内容仍有端点跟随错误

三模型已有实际 >512 tokens、自然停止、参考获准且未来 raw/compiled 正确的条件：Qwen 642、Mistral 769、Llama 578 tokens，各含三个服务重复和 6 个未来配对。Llama 使用独立声明的 192 项任务，Qwen/Mistral 使用 128 项，不能声称完全相同内容量。

Llama 的 224 项压力条件仍把目标终点 1224 写成 1124，只生成 124 项，缺少最后 100 项；显式条件为合法 JSON，但任务内容错误，拒绝认证后 raw 回退仍然错误。默认条件甚至能认证错误 raw 参考，说明相对行为认证和绝对任务正确性必须分列。

下一阶段可以另设更明确的端点/数量指令条件，在相同冻结评分下先检查 raw 是否修复，再评估认证、长度和成本。需要与原条件并排保留，不能后处理补齐序列、修改评分器或用 token padding 达标。分段生成若改变服务协议，应作为新方法单独评估，不能算原单次请求的修复。

## 5. 返修文字与额外系统能力

实验完成不等于手稿或逐点回复已经修改。下一阶段写作应逐条映射到既有审稿意见，把有限 witness、greedy 解码、动态输入范围、真实完整成本和失败回退边界写清楚。现有实验也没有测得生产环境中 query 重复频率，收益不能外推为普遍服务流量收益。

manifest 注册审计已有可检测身份错误与可信运营者错误声明的区分，但独立检查器不等于已接入全部在线路径；若进一步接入，应另测实际拒绝与零发布。CacheBlend 的现有受控适配结果也不构成跨软件栈的纯因果优越性证据。可通过收窄主张回应，或另立同栈对照实验，避免把未完成能力写成已实现。

这些是下一阶段候选工作，尚未启动新的 GPU 矩阵。优先顺序应由本轮最终独立验证、实际失败来源和用户补充共同确定。
