# 第二阶段：首轮固定输入诊断记录

这是开发诊断记录，第二阶段尚未完成。第一阶段总报告已经交付，原始数据和两例退化继续保留。

## 方法与结果

两个已知案例各使用一个新服务进程、固定 GPU，进程内重复三次。请求串行执行，使用独立 cache salt，实际观测的 prefix hit 和内部 approved-prefix read 都为 0。生成接口改用非流式响应以保留服务器返回的完整 prompt IDs，并对所有请求做精确身份核对；因此它不是原有并发、缓存和流式业务轨迹的完整重放。

| 案例 | 自由生成 | 完整 logprob 请求 | 内部验证 | 实际指标关联 | 完整/内部判定差异 | 候选布局下降 >0.03 |
|---|---:|---:|---:|---:|---:|---:|
| Llama / HotpotQA doc79 | 21 | 18 | 12 | 51 | 0 | 0 |
| Mistral / NarrativeQA doc35 | 27 | 24 | 18 | 69 | 0 | 0 |

42 个完整 logprob 请求各另生成一个 continuation token；这些是诊断操作，不属于业务吞吐样本。未经认证的候选布局也被显式生成作对照，表中候选布局不等同于获准服务请求。

每例的三次新 raw 见证都与其第一阶段失败运行当时的见证逐 token 相同。Llama 的未来 raw 输出也稳定；在本轮冷条件下，L2 未来生成没有重现原来的退化。Mistral 的 raw 对照在本轮稳定于原先较低的分数。本轮没有支持修复成功或唯一数值原因的证据。

Llama 的 L2 完整检查在见证 prompt 上最小 margin 为 0.0625，在未来 prompt 上为 0.015625，且与内部检查判定一致。部分 L0 自身 raw 路径在 teacher-forced 检查中没有全部 rank-one，而对应自由生成输出仍与见证相同。两种计算轨迹不能预设逐位相同；这些观测也不能直接证明原来的错误来自行索引。

## 指标 ID 关联修正与复核

冻结 v1 驱动对所有响应使用同一 ID 查找规则，导致 `/completions` 指标关联失败，两个原始 summary 均保留 `execution_complete=false`，冻结 launcher 也没有成功标记。没有修改或重跑这些文件。

已保存的 vLLM `serving_completion.py` 第 194 行将单 prompt 的引擎请求 ID 定义为响应 ID 加 `-0`。新增的独立 v2 审计按这一精确规则关联，检查每条 prompt 长度、完整 ID 回显、输出/usage、冻结评分、全答案/EOS 行、原始文件哈希及拒绝发布边界。120/120 个请求都关联到真实指标；它保留并解释 v1 的原始失败状态，未修改生成结果或认证准则。

本地以 `python -X utf8` 重跑 v2 分析通过；UTF-8 开关用于读取包含 Unicode 的原始 JSONL。56 个原始归档成员逐项哈希通过，恢复过程没有冲突或覆盖。源码、数据、指标、服务日志、冻结失败 summary 和加强审计都在同一归档中。

## 下一项可证伪检查

首轮候选自由生成先于认证，且各请求使用不同 salt，未读取本轮认证提交的实际 KV。这排除了该冷条件下的简单判定差异，尚未检验认证后业务复用所采用的 KV 计算轨迹。

下一轮首先固定同一见证及 L2，比较同一 prompt 的冷推理与认证提交后、同 salt 的真实前缀命中推理，再比较未来 metadata prompt；随后根据结果分离并发批形状。原失败资格化请求的 read count 为 0，只说明资格化本身没有读取先前批准的前缀，不能排除后续业务读取其新提交 KV 后的数值变化。

仅当控制能定位机制后才选择门禁或执行方式修复；已知案例不作为独立验证集。冷会话成本与长输出格式优化仍在后续阶段。
