# ContractKV：输入保真修复的开发对照与下一步决策

记录日期：2026-10-16。实验记录，尚非正式独立验证，也不是论文正文修改。

## 1. 本轮实际做了什么

完成预先冻结的四组 Qwen3-8B 对照：旧输入/raw、保真输入/ContractKV、保真输入/raw、旧输入/ContractKV。四组全部在 GPU0 上依次运行，每组为新的服务进程，16K 窗口、并发 2、相同四个已观察来源、每来源 10 租户和 10 轮，共 1600 个真实业务回答。

来源为 HotpotQA doc175、doc164，以及 RepoBench 的 IEIT-Yuan/Yuan-2.0、Jisshubot/JISSHU_BOT。每个任务家族只有两个来源，租户和轮次相关，不能把请求数当作独立来源数。

修复内容是输入协议：保留原始换行与缩进、完整问题和 CODE_PREFIX；能完整适配时保留全文，超窗时按冻结的、与答案无关的上下文裁剪规则处理；相邻同源片段在实际 Prompt 中连续呈现。四个来源中两个保留全文、两个裁剪可选上下文。

CALC、PSTP、认证作用域、margin 门槛、单次认证、收益校准、评分、生成预算和服务时钟均保持不变。没有增加输出契约变体，也没有选择新的测试来源。

## 2. 已核实的结果

以下质量和覆盖主表均使用每条件 360 对后续请求；全成本使用每条路径全部 400 个业务回答，包含在线准备、认证与等待。

| 指标 | 旧输入 | 保真输入 |
| --- | ---: | ---: |
| HotpotQA raw 平均 F1 | 0 | 0.22222 |
| RepoBench raw 平均冻结任务分数 | 0.12067 | 0.36667 |
| HotpotQA 编译后续请求 | 0/180 | 56/180 |
| RepoBench 编译后续请求 | 30/180 | 56/180 |
| 总编译后续请求 | 30/360，8.33% | 112/360，31.11% |
| 编译输出 ID 分歧 | 0/30 | 0/112 |
| 编译分数下降（任意幅度） | 0/30 | 0/112 |
| 全路由分数下降 >0.03 | 0/360 | 0/360 |
| raw 完整服务耗时 | 739.378 s | 1113.275 s |
| ContractKV 完整服务耗时 | 711.905 s | 996.887 s |
| 完整 wall 吞吐倍率 | 1.03859× | 1.11675× |
| GPU 认证调用 | 3 | 9 |

保真条件下，raw 与 ContractKV 的 360 对后续输出全部相同，任务分数也全部相同。质量改善发生在输入协议对照中，不能写成 ContractKV 通过重排提升了准确率。RepoBench 仍使用原先冻结的任务评分适配，不新增“官方完整复现”的主张。

保真输入的 800 个业务 Prompt IDs 已与独立 tokenizer 重建结果逐条核对，全部一致；候选计划也通过核对。旧输入条件同样完成实际 IDs 核查。两个条件的主分析、分层分析、输出长度和物理前缀统计均已在本地独立复算。

保真条件全部业务请求的新增 prefill token 数为 raw 3,515,512、ContractKV 2,961,864；另有认证新增 prefill 54,105 tokens，单独保留。这些是实际计数，不能转换成纯 GPU 时间的因果分解。

112 条编译请求均有实际前缀命中，其中 108 条命中量达到证书提交的前缀长度；另 4 条命中 3728 tokens，低于提交的 6768 tokens，不能写成全部完整命中。这四条分布在 doc175 的 tenant02/04/06/08、turn1。有限缓存压力是待核实的解释，当前没有逐块驱逐证据；完整成本和 prefill 表已经使用实际计数计入其损失，不另开 GPU 探针。

## 3. 仍然存在的问题：尾延迟

| 后续请求 readiness TTFT | raw | ContractKV |
| --- | ---: | ---: |
| 全局均值 | 3818.33 ms | 3330.44 ms |
| 全局 p99 | 8420.44 ms | 8562.38 ms |
| HotpotQA p99 | 8424.85 ms | 8462.57 ms |
| RepoBench p99 | 6130.99 ms | 10116.19 ms |

均值下降 12.78%，但全局 p99 增加约 1.69%；RepoBench 的条件 p99 增加约 65%。这是一次开发进程的观测，不是独立重复的总体效应；仍须完整保留，不能只报告平均值和吞吐。

已定位的直接时间来源：JISSHU_BOT 来源三个 query scope 的候选都因 candidate margin 被拒绝，各次完整 controller 耗时约 4.07–4.14 秒。两请求 wave 中，上一轮认证等待会进入下一轮 readiness 计时。示例请求 tenant00/turn1 的 controller-to-submit 为 4157.65 ms，后端 TTFT 为 6147.90 ms，readiness TTFT 为 10305.55 ms。相同位置 raw 的 controller-to-submit 为 18.99 ms。

这支持“同步失败认证增加部分请求等待”的执行账本解释。它不证明全部尾差异都只有一个原因，也不支持把验证等待从成本中扣除。

## 4. 门禁与契约的诊断

保真条件的事前收益门禁没有拒绝 scope。该场景预先声明高复用，估计可节省的工作大于估计认证成本，所以全放行本身不构成实现错误。

但旧校准来自短输入，长输入的实测认证成本存在低估。JISSHU_BOT 的事前预测成本约 1.64 秒，而完整 controller 实测约 4.1 秒。是否采用输入长度相关的成本适配，需要另行冻结与验证，不能直接在本轮结果上改门槛后继续沿用“输入修复唯一变化”的解释。

后续 CPU 审计补充分解：上述 1.64 秒是前置概率加权期望总成本。首个 scope 的条件 GPU 预测为 2027.33 ms，见证 eligibility 通过后的条件总预测为 2152.35 ms；对应实际 RPC 为 4033.56 ms、完整 controller 为 4141.65 ms。比较预测误差应采用这些匹配的条件与时钟，不能直接用 4.1/1.64 作为 GPU 缩放倍数。

旧输入有一次 Python 语法准入拒绝；保真条件没有 Python 语法准入拒绝。当前结果没有提供必须新增 next-line 契约变体的依据。因此本轮不取消语法保护、不放松安全 margin、不扩大动态作用域。

## 5. 建议与决策边界

我的建议是保留现有机制，先完成已经约定的一次独立来源验证。当前开发结果同时支持输入保真、非 RULER 编译覆盖、行为保持和完整成本正收益；不应只为这一次 p99 结果扩展新的认证算法。

若决定先处理尾延迟，候选方向应限于已有收益门禁的成本估计与预算适配。它将构成单独的方法变体，需要先在开发来源冻结规则和额外对照预算；不能无声更改当前四组或重新放宽作用域。

在收到用户对这个实质性权衡的意见前，不启动新的 GPU 分支。CPU 审计、证据归档和已有结果复算继续完成。
