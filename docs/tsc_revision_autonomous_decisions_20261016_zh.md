## D03：发布身份不是完整物理驻留证明

**依据：** 开发对照有四次 3728/6768 tokens 的部分前缀命中；现有控制器记录的是已发布 hash，缺少逐块驱逐证明。

**决定：** CPU 审计把“观察到发布”“曾命中”“当前完整驻留未知”分开。成本适配不得把前者改称后者；无法确认时可考虑保守成本，但不先认定驱逐是唯一原因。

## D07：成本差额必须使用相同条件与时钟

CPU 逐字段核对发现，常说的 JISSHU_BOT“预测 1.64 秒”是前置门禁乘以 eligibility 概率后的**期望总成本**，不能直接当作一次实际 GPU 认证的条件预测。首个 scope 的 GPU 成本预测为 2027.33 ms，前置信息成本为 125.02 ms；见证通过 eligibility 后的预测总成本为 2152.35 ms。实测 GPU RPC 为 4033.56 ms，完整 controller 为 4141.65 ms。

**决定：** 分别核对前置期望成本、条件 GPU RPC、信息成本和完整 controller，不用混合时钟夸大预测失配。长输入的实际低估仍然存在，但不能简单按 4.1/1.64 的比值选缩放因子。仅修正成本预测也不必然拒绝该来源：当前声明的高复用使其预计总收益仍远高于成本，尾部等待预算必须独立评估。

## D08：只保留一个成本候选，先做有界三路开发对照

**候选：** 按模型/任务/档位和固定长度桶构建冷认证实测上包络，未知当前完整驻留时仍按冷成本；保留旧收益 cap 和概率项。fan-out 另设明确的增量同步 controller 预算，取已有 DEV raw 全局 p99，不把原来的总 TTFT 判断简单打开。仅 Qwen 有长输入开发成本，因此候选实测先限 Qwen。

**离线结果：** 在已知保真四来源账本中，候选会跳过 9 次原 GPU 尝试中的 3 次，原获准的 4 个 scope 仍全部允许。它是反事实 CPU 分析，不能写成实际省下 wall 或已经降低 p99。

**决定与上限：** 主 18 单元先完成、不受该规则影响；之后只跑一次 Qwen 三路 DEV（fresh raw、原版、适配版，共 3 cells）。仅满足预先写下的质量、覆盖、完整 wall 与目标 RepoBench p99 条件，才执行最多 9 个 Qwen 三路/三重复独立单元。独立成本来源另选，排除既往 567 个及本轮主验证六个；不复用已经运行中的主六来源作“完全未见”成本测试。条件不通过即保留负结果，不继续搜索参数。新增预算最多 12 cells，无新任务家族、模型或调度器。
