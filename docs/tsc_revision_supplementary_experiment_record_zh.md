## 3. 实现修补的语义

原部署模式在既定 prospective route qualification 后，使用代表性 compiled prompt 路径作部署 attestation 参考。R1R 开始的保守模式，以 exact query 首次真实 raw 业务回答作见证。两者必须分开解释，后者不是只增加了一个 if 检查。

R2/R3 增加实际完整 Prompt/输出 IDs、逐 token 与自然 EOS margin、固定单次候选、收益门禁和有限 Python 输出准入。R4 继续使用 `(namespace, query_scope)` 决策，收紧经验共享资格并引入带成本/尾预算的既有准入修补。没有新增两个独立签名或生命周期的证书系统。

静态源码审计比较了具体 R1R-slice 和 R2-margin 后端，PASS 后发布分支 AST 一致。它支持发布分支未被该项准入修补替换，不能代替 live 拒绝/零发布实验，也不能证明原系统所有源代码字节都没变。

控制状态按模板身份和行为 scope 分别计数。若有 T 个模板、U 个行为 scope、M 个请求，当前保守模式保存 O(T+U) 状态，形成 O(U) scope 决策，每个被选 scope 最多一次 GPU 认证。只有固定每模板 U 时，才可说完整认证相对 tenant 数量摊销；唯一 query 流不具有通用 O(1) 行为认证成本。生产 query 重复频率未测。

## 4. 共同非 RULER 证据与基线比较

共同 HotpotQA 使用相同 30 sessions、三模型三重复，共 2430 个未来配对。新 prefill 降低分别为 Llama 38.38%、Mistral 40.69%、Qwen 48.05%；该组没有 >0.03 分数下降，但输出 IDs 并非全部相同。零 slack 固定三模型宏平均净 TTFT 改善 5.242%，95% 来源簇 CI [-2.162,12.564]%。

该区间描述三个固定模型在共同 scope 的平均效应，不是架构总体预测区间。任务绝对质量、认证覆盖、raw fallback 与完整成本必须一起报告；物理 prefill 降低不能自动解释成所有冷会话净收益。

CacheBlend 等四方法共有 9000 个 native-matched 配对，每方法 2250。在阈值 >0.03 下，CacheBlend 有 224 次下降、331 次上升，均分 0.333210→0.339817；ContractKV 有 2 次下降、0 次上升，均分 0.353780→0.353744。两条 native raw 基线不同，不能据此计算 112 倍因果安全排名或跨栈 2.18% 因果速度优势。

## 7. 完整成本、治理与安全

原四配置补测全成本净 TTFT 改善分别为 Qwen +17.50%、Mistral -2.84%、Llama +7.69%、14B TP2 +10.59%。历史没有记录的参考生成、失败尝试等时钟继续标为不可得，不能用新测四配置精确替代原 Table III 完整策略数字。

所有新服务完整 wall 都计入实际首次 raw、业务生成、计划准备、logprob/认证、失败尝试、同步等待、评分与日志。服务进程启动和一致的基础设施前测另行记录；重叠 RPC 累计时间是工作量描述，不能再次加到已测 wall 上。

D1/D2 两组各 20 个控制案例中，各自 10/10 坏布局被拒绝，拒绝发布 tokens 为 0。14B 另有真实后决策输出质量控制。原 D1 goodput 1.472、D2 1.428 保留：D2 的价值是准入和事务发布治理，不保证比已知安全 D1 更快。

Manifest 有 9 个独立 CPU 案例，7 个拒绝；合法声明与可信运营者正确签名但语义错误的私有声明都能被接受。CPU helper 未接入 live endpoint。哈希证明字节身份，不证明应否共享或保密性。

原型未实现缓存时序通道防御。P4 是缓存状态隔离，授权域内的命中延迟推断仍不解决，不把它当作应用安全边界。325000 次状态机压力操作是 CPU 工作，4695 个 segment 位移是受控输入分析，均不等于生产 GPU 服务请求或生产发生率。

## 9. 历史输入问题与修复

代码溯源确认，词数截断和空白折叠不只影响 R4，也影响原稿和多个历史补强队列。R4 的 HotpotQA 有 8/10 来源答案字面串在截断后消失；另 1 个在存储原文中也找不到完整字面串，只有 1/10 在实际输入保留完整字面串。RepoBench 为 5/10 CODE_PREFIX 裁空、2/10 部分保留、3/10 全保留，全部 10 个换行/缩进被折叠。

字面串代理不等于语义可回答性；NarrativeQA 的抽象答案和代码下一行也不能仅按字面缺失判坏。原稿物理复用、治理证据不因此自动失效，但任务质量与代表性的解释需要重新限定。

原 Table I 的 85.0/2.4 及 82.4/2.1 尚无闭合的原始数据、renderer、token 统计和分母链。固定版本 Azure 示例仅支持 query/history 在 Sources 前的条件性布局动机，不支持这些原百分比、生产重复率或真实服务收益。未伪造重建。

修复采用共同 16K tokenizer 窗口；保留完整问题和 CODE_PREFIX、原始空白与顺序。可选上下文按固定原始段落/行 head-tail 裁剪，有明确 omission 记录，禁止使用答案、位置、模型分数或认证结果选片。

进一步的 CPU 预检发现，保存片段文本还不够：旧内部 chunk 标题会插入代码中间。因此只合并相邻、连续、同原 segment 的显示标题，不改变 CALC 节点、顺序、层级和依赖边。CODE_PREFIX 类型一致性修正对所核对 200 个布局不改决策，不能把它包装成速度提升原因。

最终准备的 50 个已知来源中，32 个全文保留、18 个仅裁可选上下文，0 个关键字段不支持；全部声明的三模型、tenant/turn raw 与实际候选均预检 fit。该 CPU 准备约 398.91 秒，是 raw/策略共同的不可变 benchmark 输入准备，单独报告，不冒充在线 GPU 成本。
