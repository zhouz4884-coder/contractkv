# ContractKV TSC Major Revision — Final Experimental Strengthening and Evidence Closure

## 一、总目标

继续完成 ContractKV 在 IEEE Transactions on Services Computing（TSC-2026-07-1067）大修中的实验补强。

本阶段的目标不只是“补齐审稿人要求”，而是以**原有 CALC、Scoped Behavioral Certification、PSTP 和 Service-Template Certificate 四项机制**为中心，建立更加有力的系统论文证据：

**证明 ContractKV 能够将结构上可复用的 Prompt 内容，转化为具备行为准入、事务发布和授权跨租户复用能力的 KV 服务状态，并在真实任务与完整服务成本下产生可测量的性能收益。**

重点回答五个科学问题：

1. 完整在线资格成本计入后，原部署性能主张还能成立到什么程度？
2. CALC、行为认证、PSTP 和模板共享各自贡献什么能力，为什么仅进行布局重排不足以实现相同的系统语义？
3. 在真实任务输入、自由生成和 Open-arrival 服务条件下，质量保持与 Goodput 收益能否在同一个协议中成立？
4. 认证资格覆盖、物理前缀命中、验证开销和尾延迟之间有什么实际关系？
5. 多租户共享状态的身份绑定、授权与事务可见性，实际由哪些代码路径实施，哪些风险属于可信运营者的责任？

**不重新设计 ContractKV，不新增算法作为完成任务的前提，不为了改善数值放宽行为准入，也不将现有技术简单拼接包装成未经证实的新发明。**

优先通过可复核的机制实验，证明已有设计的必要性、实际系统价值和独立贡献。

## 五、第三批：Manifest、Binding 与实际 KV 发布闭环（必须完成）

沿用现有 9 个注册 CPU 案例、19 个客户端绑定检查及冻结的合成敏感标记场景。

重点区分四个执行环节：

1. Manifest 注册声明；
2. 受信任客户端的 HMAC/Scope Binding；
3. 实际 GPU 认证与 PSTP 发布；
4. 后续请求的物理 KV 命中及原生 APC 行为。

只使用人工合成敏感标记，不使用真实个人、医疗或其他私密信息。

必须覆盖：

- 非法注册主体及伪造身份；
- 过期签名、版本、策略和生命周期；
- 显式 PRIVATE/MUTABLE 共享冲突；
- 同授权域合法复用；
- 可信运营者的语义误标；
- 不同 observation 内容；
- 相同及不同稳定前缀字节身份；
- 实际 raw fallback 与编译共享路径。

特别要求：

- 注册 Helper 的 CPU 结果不能直接写成在线 GPU 隐私实验。
- Binding 拒绝 compiled 不等于原生 raw APC 没有命中。
- PSTP 零发布指的是被拒 compiled candidate state，不是整个缓存系统零存储。
- Hash/HMAC 证明身份与字节匹配，不推断内容的公开性。
- 实验采用受信任内部编排器边界，不得虚构已实现的公网 IAM Proxy。
- 不能声称已有时序侧信道防御。

单独输出一份 **Trust Model / Enforcement Boundary Matrix**，明确每个检查实际执行的位置、对象、失败结果与未覆盖风险。

## 六、第四批：任务保真 Open-arrival 与服务级性能桥梁（新增，优先级高）

前三批完成并归档后，开展一项独立冻结的 **Task-Faithful Open-Arrival Serving Validation**。

目标是将此前分开证明的三件事放进同一实验：

**任务质量保持、合法 KV 复用、真实 SLO 服务收益。**

### 6.1 任务与输入

使用已冻结的 16K 保真输入规则：

- 完整保留问题与关键 CODE_PREFIX；
- 保留代码换行、缩进和原始任务结构；
- 超窗时只按事前固定规则裁剪可选上下文；
- Raw 与 ContractKV 使用相同保留内容。

优先选择新的 source-disjoint HotpotQA 和 RepoBench 来源，建议至少各三个。

来源选择依据预先确定的哈希顺序及既有排除集合，不依据任务答案、吞吐或已知资格结果筛选。

### 6.2 算法条件

只比较：

- Native APC / Raw；
- 当前冻结的 Query-qualified ContractKV。

不得改变 margin、query scope、EOS、评分、PSTP 或成本门禁。

### 6.3 服务负载

先进行 Raw-only 负载标定，确定轻载、中载及接近饱和的实际可执行区间。

在任何 ContractKV 正式结果产生之前冻结：

- 到达轨迹；
- Offered load；
- TTFT/TBT 或端到端 SLO；
- 请求数及任务来源；
- 客户端并发与队列压力；
- 服务端 `max_num_seqs`；
- 统计单位与重复次数。

不要直接假定两张 RTX 3090 可以同时驻留 8/16/32 条长上下文请求。

必须分别记录客户端到达压力、排队请求数、实际 GPU 活跃请求数，以及显存和 KV 容量约束。

### 6.4 有界执行规模

第一阶段：Qwen3-8B，两个预先确定的负载点，Raw/ContractKV 各三次新进程配对，最多 12 个正式 cell。

通过执行可行性检查后，扩展至 Mistral 和 Llama 各一个共同负载点，每模型 Raw/ContractKV 三次配对，额外 12 个 cell。

如需更高负载点或额外 SLO，只能依据**事前冻结的负载覆盖规则**扩展，并作为明确的独立批次，不得因当前倍率不够高而增加有利点。

### 6.5 必须报告

- SLO-compliant Goodput（绝对 req/s 和相对 Raw）；
- Offered/achieved throughput；
- Mean/P95/P99 TTFT；
- TBT/TPOT；
- 完整请求端到端延迟；
- Raw/Compiled 实际任务分数；
- 输出 Token ID 分歧及升降分；
- 合法编译覆盖率；
- GPU 认证 PASS/FAIL/INCOMPLETE；
- 实际物理 Prefix-hit tokens、new-prefill tokens；
- 队列长度、活跃请求、KV 池容量与重算；
- 全部在线认证、失败尝试与等待成本。

SLO 必须从**预定到达时刻**计算；不能只从真正送入 GPU 的时间开始计时并排除上游资格等待。

保留每来源和每次进程结果，使用合适的来源簇不确定性统计，不能把租户轮次当作独立来源。

**验收问题：在保真任务的真实到达压力下，ContractKV 是否能够同时维持可观察的行为保持并获得有意义的 SLO Goodput？**

不要求结果一定优于原 4.81× 工作点。新协议不能与旧部署协议直接合并倍率。

## 七、第五批：机制消融与尾延迟归因（新增，有界）

本批先执行 CPU 分析，只有存在明确实验必要性时才启动附加 GPU。

### 7.1 CALC 布局阶梯

在冻结输入上对 L0/L1/L2/L3 分别统计：

- 依赖合法性；
- Segment/token 位移；
- 真实完整渲染后的稳定前缀长度；
- 可实现的 block-aligned 前缀上限；
- 不同模型 Tokenizer 下的结果。

必要时对预先选择的小规模代表来源进行 GPU 质量和认证对照。

**不得将原部署 Ladder 与 R4 的单候选实现混成同一个在线算法。**

### 7.2 Benefit Gate ON/OFF

在相同输入、模型、scope、认证和 PSTP 条件下，比较：

- 原冻结经济收益门禁；
- 仅关闭经济收益判断、保留全部行为安全验证的控制变体。

比较实际 GPU 调用次数、无收益认证、合法覆盖、完整 wall、Mean/P99 及 Goodput。

Gate OFF 绝不能绕过行为认证或事务发布。

使用新的独立冻结来源；如只做离线反事实模拟，必须明确不能推断真正的排队和认证成本。

### 7.3 Margin 敏感性

优先利用已归档 logits/margins 进行 CPU 离线分析，考虑包括现有 0.0625、0.125 在内的事前固定阈值集合。

报告不同阈值下的候选资格变化、已知有害案例、覆盖损失。

**不要将离线 Margin PASS 等同于新的未来自由生成安全保证。**

尤其说明 NarrativeQA 的 0.40625 反例：提高单次轨迹的 margin 不能代替 Scope Binding。

### 7.4 P99 Tail Forensics

对既有保真主验证和新增 Open-arrival 中的慢请求进行逐请求时序归因：

- source / tenant / turn / scope；
- L0 / compiled / raw；
- controller-to-submit；
- raw witness、GPU verification、PASS/FAIL；
- 实际排队时间与后端 TTFT；
- 下一轮 readiness 传播；
- prefill、native hits 和 KV 回收；
- 请求输出长度和 EOS；
- 每个来源的慢请求集中程度。

计算慢请求中可观察的认证等待贡献，区分同步资格等待、物理缓存重算、排队及长输出。

仅当诊断确认一个可修复的现有执行问题，才允许提出最小缓解，并进行单独冻结的 A/B。

不能通过无依据地拒绝更多合法 scope 来宣称修复 p99。已有成本适配负结果必须作为对照保留。

### 7.5 PSTP 贡献

复用已有失败、取消、超时、重复提交、资格冲突和 native reclamation 审计。

若现有证据完整，不再重复 GPU 压力测试。

不得通过真实共享未经认证的状态，构造不安全的性能消融。

## 八、实验独立性与禁止事项

所有实验必须遵守以下规则：

1. **先冻结后执行。** 来源、策略、模型、预算、评价方法、SLO、到达轨迹、成本口径和停止条件，在读取正式结果前全部固定。
2. **不得按结果调参。** 可以修复明确的基础设施或代码兼容性错误，但必须版本化、记录前后差异，并通过独立检查。
3. **历史数据不可覆盖。** 原稿、R1–R4、失败成本变体、旧 Table I/Table III、部分固定到达结果全部保留。
4. **不同协议不混合。** Deployment-qualified、Query-qualified、旧 Renderer、保真 Renderer、Closed-loop、Open-arrival 各自统计。
5. **行为保持不等于绝对正确。** 同时报告 Raw 绝对任务分数、Compiled 分歧及全路由变化。
6. **拒绝率必须使用实际分母。** 不将预设风险样本全部视为已发生行为损坏的候选。
7. **不使用虚构的运行时能力。** 不实现了就不能声称自动协议切换、公共鉴权代理、独立双证书或生产级侧信道防御。
8. **不得推断 GPU 因果时间。** Prefill tokens 是真实工作量指标，不能直接换算成 GPU 时间。
9. **保留所有负结果。** 包括负收益、错误拒绝、尾延迟恶化、未命中、未完成输出及失败认证。
10. **不得无限拓展。** 新实验必须对应一个明确审稿问题或机制假设；完成冻结矩阵后停止，不因倍率未达预期追加有利测试。

## 九、资源与执行纪律

主体开发和性能测量使用两张 RTX 3090 24GB。

所有环境、缓存、日志、源码快照、数据与临时文件原则上放在指定 8TB 卷，避免填满系统盘。

运行前：

- 刷新 GPU/PID/显存清单；
- 检查当前 worker 与锁；
- 确认 GPU 真正空闲；
- 不终止、不抢占其他任务；
- 不与其他 GPU 作业混跑正式性能；
- 重新检查必要的模型权重、Tokenizer、Runtime 源码及 SHA。

如果 GPU 忙，进入等待与只读监测，不启动竞争任务。

正式实验只在获得 GPU 独占条件后开始。基础设施失败必须保存原始日志，不允许静默续跑半个 cell。

所有实验必须生成原始运行记录、完整请求级计数及独立复算结果。
